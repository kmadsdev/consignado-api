# Decisions

One row per decision. "What a bank would do" is the honest distance between this demonstration and a production system.
The five largest decisions also have an ADR; the row links to it.

Back to the [entry page](README.md).

## Hosts and gateway

| Decision | Why | Trade-off | What a bank would do |
|---|---|---|---|
| **Two hosts for one unchanged jar.** The same build of the API runs as pods on AKS and inside an Azure Function. Both use the same database. ([ADR 0007](../adr/0007-two-hosts-one-api.md)) | The comparison "Kubernetes against serverless" is fair only when both run the same program. | Two deploy paths to keep working. The outbox relay runs only on AKS, so an event written on the serverless host waits for a running pod. | Choose one host per service from load and cost data, and keep one deploy path. |
| **Custom handler on Azure Functions.** The Functions host starts a bundled Java runtime and forwards each HTTP request to Spring Boot. | It runs the artifact that CI already tests. A rewrite as Java functions, or the Spring Cloud Function adapter, would be a second artifact. | A JVM cold start of 18.6 s to 18.9 s, measured live through the edge (the local measure under emulation, 11 s to 12 s, was too low). A 129 MB package. A Java runtime that must be patched by a new build. Functions is used against its grain. | Use a container platform for a Spring Boot service, or invest in a native image or checkpoint/restore to cut the start time. |
| **The gateway is the only public backend.** The two API hosts accept calls only from the gateway. The API has no login of its own. ([ADR 0008](../adr/0008-gateway-in-front-of-two-hosts.md)) | One place for the token check, the quotas, the trace and the audit log. The API stays unchanged. | The network is a single line of defence for the API. The gateway is a single point of failure. | Add service-to-service authentication (mTLS or a token that the API validates), and use a managed API gateway product. |
| **The gateway is plain Java with a ports-and-adapters core.** The rules are in `core/` with no Azure type. Azure calls are behind interfaces in `ports/`. | The rules can be tested with no network: 82 tests run against in-memory fakes. Java matches the API, so one language covers the backend. | The adapters have little test coverage. Their first live run found faults that no fake could show: a setting name, the log text, the ARM request headers, a node list that the role cannot read (see the [lessons](operations.md#9-lessons-from-the-first-day)). A JVM function has its own cold start (first gateway calls 3.0 s to 3.9 s). | The same structure, plus contract tests of each adapter against the real service in a test subscription. |
| **Internal load balancer and a VNet-integrated function.** The AKS Service has only a private address. The gateway reaches it through the virtual network. | The cluster has no public entry for the API. The old rule "allow one public address" is gone. | The fixed private address is set in two places (manifest and gateway setting). The gateway subnet has no NAT gateway (it would cost about US$32 per month), so outbound calls use the Azure default path. | Private endpoints for every data service, a NAT gateway or firewall for outbound traffic, and a service mesh inside the cluster. |
| **Azure RBAC for Kubernetes, local accounts off.** Every caller of the Kubernetes API gets a token from Entra ID. The gateway can read (it cannot list nodes). CI deploys inside the namespace `consignado` only (`RBAC Admin` at namespace scope). My own account is cluster admin and creates the namespace once. | One permission system, declared in Terraform. No kubeconfig file with a client certificate exists, so none can leak. | `kubectl` needs `kubelogin`. A mistake in a role assignment locks people out until Terraform is applied again. | The same, plus privileged access on request with approval and a time limit. |

## Cluster, edge and sign-up

| Decision | Why | Trade-off | What a bank would do |
|---|---|---|---|
| **Cold cluster on demand, fixed windows, a cool-down.** The cluster is stopped by default. A user starts it for 15 minutes. After each stop, 15 minutes of cool-down. ([ADR 0009](../adr/0009-cold-cluster-and-access-windows.md)) | A running node costs US$0.104 per hour; left on for a month it is about US$76, more than the whole budget. One window costs about US$0.04 of node time including the start and the stop (US$0.026 for the 15 minutes alone). The cool-down follows the AKS guidance to wait between a stop and a start. | The first user waits minutes for the start. A second user can be refused during the cool-down. | Keep the cluster running, with autoscaling and reserved capacity. Availability is worth more than the node cost. |
| **Cloudflare Worker as the edge in place of Front Door.** ([ADR 0010](../adr/0010-cloudflare-edge-instead-of-front-door.md)) | Azure refused Front Door: `Free Trial and Student account is forbidden for Azure Frontdoor resources`. The DNS zone was already at Cloudflare and the Worker costs nothing. Front Door Standard would also add US$35 per month and put the fixed cost over the budget. | One part of the request path is not Azure. No managed WAF rule set; the zone has three custom rules (40 requests per 10 seconds per IP on `/api/`, a method allow-list, a managed challenge for non-browser clients on the two write routes of the forms). The Cloudflare address list in the gateway must be updated by hand. One shared secret (the edge key). | Front Door Premium or an equal product: managed WAF rule sets and a private link to the origin. |
| **Sign-up in my own tenant, with restricted guests, in place of External ID.** A self-service sign-up user flow with an email one-time code. ([ADR 0011](../adr/0011-sign-up-in-the-workforce-tenant.md)) | A separate Entra External ID tenant was refused by the region policy of the subscription. The user flow needs no password and no social login. | Visitors become guest users in the tenant that also holds the subscription. Guest permissions were set to the most restricted level and invitations were limited to admins. | A separate customer identity tenant, with no link to the tenant that manages the infrastructure. |
| **Turnstile on the forms.** The contact form and the profile form send a Turnstile token; the gateway verifies it with Cloudflare. | A free check that stops simple scripts before they create contact rows or accounts. | The check fails open: without the secret in Key Vault the gateway accepts the form and logs `bot check not configured`. The secret is in Key Vault, and the check was verified live (a visible browser passes, a headless one is refused). A person can still abuse the forms by hand. | A bot management product plus fraud scoring on sign-up. |

## Data

| Decision | Why | Trade-off | What a bank would do |
|---|---|---|---|
| **Database with a public endpoint and the "Azure services" firewall rule.** The server is in `northcentralus`; the small size had no capacity in `belgiumcentral`. | I chose it for cost. A private endpoint costs about US$8 per month plus a private DNS zone (estimate), and the server is in another region than the virtual network. | Any Azure tenant can reach the port. The password (28 random characters, only in Key Vault) and TLS are the real controls. The function apps and the database are in different regions, so each query crosses regions. | A private endpoint or VNet injection, no public access, Entra ID authentication for the database, and the same region as the callers. |
| **Shared data is append-only, with one guarded change.** No `DELETE` and no free update exists. The one exception changes a customer's income and is refused when the new margin is below the committed installments. ([ADR 0007](../adr/0007-two-hosts-one-api.md)) | All users see the same data. Nobody can destroy what another user is looking at. | Test data only grows. Cleaning it is an operator task on the database. | Per-tenant data with row-level security, and an audit log inside the API. |
| **Stateless preview and browser-only data for guests.** A guest can call one endpoint that has no repository. The guest's inputs stay in the browser. Guests see a masked snapshot of the shared data. | A visitor with no account cannot write to, or read from, the database. The rule is enforced in the gateway and again in the API code (a test proves that the preview has no data source). | A guest does not see the real workflow. The snapshot keeps salary values, without a readable name or CPF. | The same idea: public calculators never touch customer data. |
| **Duplicate-account rule and hashed identifiers.** Same device fingerprint as another account: the new account is held for the admin's approval. Same IP address only: a flag, the account stays active. Addresses and fingerprints are stored only as HMAC-SHA256 with a key from Key Vault. | The limit of 3 windows is per account, so a second account is the easy way around it. An office or a university shares one IP, so an IP match alone must not block. A leak of the table does not show addresses. | A new browser or a VPN passes the check. It is a filter, not a proof. The admin approves held accounts by hand. | Verified identity at sign-up, device intelligence, and a risk team. |

## Money and operations

| Decision | Why | Trade-off | What a bank would do |
|---|---|---|---|
| **A budget alert that pauses the engine.** R$ 330 per month (about US$60); Azure bills this subscription in BRL. Alerts at 50, 80 and 100 percent go to me by email. At 100 percent an action group calls a gateway webhook: the engine is paused and the cluster is stopped. ([ADR 0012](../adr/0012-budget-guard-and-abuse-limits.md)) | The largest variable cost is the running node. Stopping it is the one automatic action that cuts spend and deletes nothing. | **It is not a hard cap.** An Azure budget sends alerts and stops nothing by itself; the alert comes after the spend is recorded (general Azure behaviour, not measured here); and the fixed costs (database, registry, disk, public IP) continue. Delivery of the alert was not verified. The webhook URL holds a function key, so it is not in a file: Terraform reads it from `TF_VAR_budget_webhook_url`, and an apply without that variable removes the webhook. | Budgets per team with forecasts, anomaly detection, and capacity that is paid in advance. Nothing stops production on a budget alert. |
| **Terraform with remote state and no secrets in outputs.** State is in a storage account with Entra ID sign-in only, no account key, versioning on. `outputs.json` is committed and holds names only. | The whole stack can be read, reviewed and made again. A reader can see the real names without any secret. | The database password exists in the state (it is generated there), so the state storage must stay private. I apply Terraform by hand from my own machine. Front Door code is kept behind a flag that is off. | A pipeline that plans on a pull request and applies after approval, policy checks on the plan, and secrets generated outside the state. |
| **IDs as GitHub secrets only to mask them in public logs.** The client id, tenant id and subscription id of the deploy identity are stored as repository secrets. | They are not secret: OIDC login needs no password. As secrets, GitHub masks them in the logs of public repositories. | A reader could think that a password is stored. This page says that none is. | The same, in private repositories with protected environments and required reviewers. |

## Example

A recruiter opens the site on a phone and tries the loan preview with no account. That call uses the serverless host and never reaches the database (guest rule). The recruiter then signs up with an email code, completes the profile, and asks for a window. The gateway finds no other account on the same device, so the account stays active, and the cluster starts. Fifteen minutes after the window opens, the gateway closes it and stops the cluster. The cost of that visit was about three cents of node time, and nothing that the recruiter did could delete another user's data.
